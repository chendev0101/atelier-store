# Database change

A schema change in this project touches six places, and the failures are quiet: a column missing from the seed's upsert list never updates existing rows, and drizzle-kit can fail while still exiting 0. Work through the steps in order, and stop where the plan says to stop.

Read `CLAUDE.md` first if it is not already in context: it describes the dependency chain (`env.ts → db → auth.ts`) and the catalogue cache rules this skill relies on.

## 1. Classify the change

Decide which kinds of change the request contains, because they carry different risks:

| Kind | Examples | Risk |
|---|---|---|
| Additive | new nullable column, column with a default, new table, new index | Safe |
| Tightening | `NOT NULL` on an existing column, new `check`, new unique index, narrower type | Fails at migrate time if existing rows violate it |
| Destructive | drop column or table, type change that loses data | Data loss |
| Rename | column or table rename | drizzle-kit needs an interactive answer; see "Renames" in step 3 |

Adding a `NOT NULL` column without a default to a table that has rows is a tightening change: Postgres rejects it. Give it a `.default(...)`, or add it nullable, backfill, then tighten in a second migration.

Tell the user the classification in one or two lines before editing anything. For destructive changes, also say what data will be lost and ask whether to proceed.

## 2. Edit the schema

- Tables live in `src/db/schema/*.ts`. A new table in a new file must be re-exported from `src/db/schema/index.ts`; both `db` and drizzle-kit read only that entry.
- Schema files must not import `server-only`: drizzle-kit and the seed script load them outside Next.js.
- Follow the existing style in `catalog.ts`: snake_case column names in SQL, camelCase in TypeScript, a short `/** doc */` on non-obvious columns, the shared `timestamps` spread on new tables, `uuid().primaryKey().defaultRandom()` ids, money as integer cents, a `check` for invariants like non-negative amounts.
- Add `relations(...)` for new foreign keys so `db.query.*.findMany({ with })` works.
- Don't add an index on a low-cardinality column (like a boolean) of a small table; Postgres won't use it.
- Better Auth tables are generated by its CLI (`pnpm dlx @better-auth/cli generate`), not written by hand.

## 3. Generate the migration

```bash
pnpm db:generate --name <snake_case_description>
```

Always pass `--name` (e.g. `product_launched_at`, `add_reviews`); the default random names say nothing in `drizzle/`.

**Then check that a new `drizzle/NNNN_<name>.sql` exists.** drizzle-kit asks interactively when a diff could be a rename (a column or table disappears and another appears in the same change). Claude's shell has no TTY, so it prints `Interactive prompts require a TTY terminal` and **still exits 0** without writing anything. Don't report a migration you haven't seen on disk.

drizzle-kit reads `DATABASE_URL` from `.env.local` for its config but `generate` never connects to the database.

### Renames

Let drizzle-kit write an empty migration and fill it in yourself, then repair the snapshot:

1. With the schema already renamed, run `pnpm db:generate --custom --name <name>`. It writes an empty `.sql` and a snapshot copied from the previous one, so the snapshot still has the old name.
2. Write the SQL: `ALTER TABLE "t" RENAME COLUMN "old" TO "new";` (or `ALTER TABLE "old" RENAME TO "new";`).
3. In the new `drizzle/meta/NNNN_snapshot.json`, rename the column: both its key under `columns` and its `"name"`, plus any index, foreign key or check that mentions it. For a table rename, rename the table key and `"name"` and every reference to it.
4. Run `pnpm db:generate` once more. It must print `No schema changes, nothing to migrate`. That line is the proof the snapshot matches the schema; if it tries to generate anything else, fix the snapshot until it doesn't.

If the snapshot can't be made to match, discard the migration (see step 4) and ask the user to run `pnpm db:generate --name <name>` in their own terminal and choose "rename" at the prompt.

Never accept a rename as a drop plus an add: that deletes the column's data, and adding a `NOT NULL` column to a table with rows fails anyway.

## 4. Review the SQL, then stop and ask

Open the generated SQL and fix what drizzle-kit can't know:

- **Type changes**: drizzle emits `SET DATA TYPE` without `USING`; add `USING col::newtype` (or an expression) when Postgres can't cast implicitly.
- **Backfills**: a new column's default applies to every existing row, which is often meaningless (a `launched_at` defaulting to `now()` makes every product launch today). If existing data gives a better value, add an `UPDATE` after the `ADD COLUMN`, e.g. `UPDATE "products" SET "launched_at" = "created_at";`. For tightening changes, put the `UPDATE` before the `SET NOT NULL`. Separate statements with `--> statement-breakpoint`.
- Editing the `.sql` is fine; the snapshot tracks the schema, not the SQL.

Then **paste the full SQL into your reply as a code block**, not a prose description. The user is approving these exact statements. Add a one-line summary of the effect on existing rows, call out every `DROP`, `RENAME`, `SET DATA TYPE` and `SET NOT NULL`, and **wait for approval before migrating**. Offer to run the migration yourself once they agree, rather than handing them the command. `pnpm db:migrate` writes to the shared Neon database and there are no down migrations; once applied, undoing means writing another migration.

To discard a migration that has *not* been applied: delete the `.sql` and its `drizzle/meta/NNNN_snapshot.json`, and restore `drizzle/meta/_journal.json` with `git checkout`. Never use `pnpm db:push` (prototyping only; it skips the migration history).

## 5. Carry the change through the code

Do this before migrating, so typecheck can catch gaps:

1. **Seed** (`src/db/seed/`): add the field to the `Seed*` type and data in `catalog-data.ts`, to the `.values(...)` mapping in `index.ts`, **and to the `excluded(...)` list in `onConflictDoUpdate`**. Without that last one, re-seeding inserts the value for new rows but silently leaves existing rows unchanged. For a dropped or renamed column, remove or rename it in all three.
2. **Domain types** (`src/lib/catalog.ts`): add the field to `Product` / `Category` if pages need it. These types are what the UI sees; keep DB-only details (ids, timestamps) out unless a page needs them.
3. **Mappers and queries** (`src/db/queries/catalog.ts`): update `toProduct` / `toCategory`. New query functions follow the existing pattern — `"use cache"`, `cacheLife("minutes")`, `cacheTag("catalog")` — because `cacheComponents` requires it. Pages read the catalogue only through this file.
4. **UI**: update the components or pages that should show the new data. If a hand-written list in `src/lib/storefront-content.ts` becomes redundant because the data now lives in the DB, remove it rather than keeping two sources of truth.
5. Run `pnpm typecheck` and `pnpm lint`; both must pass.

## 6. Migrate and seed (after approval)

```bash
pnpm db:migrate
pnpm db:seed      # only if seed data changed; it resets inventory quantities
```

Mention that `db:seed` resets stock before running it.

## 7. Verify

- Query results are cached for minutes, so the dev server may serve old data right after migrating. Wait for the change instead of assuming it failed: poll with `curl` in a background loop until the expected text appears (no foreground `sleep`).
- In app code that writes catalogue data, call `updateTag("catalog")` after the write so pages refresh at once.
- Check the pages that use the changed data, not just that they return 200: an unknown slug inside `<Suspense>` also returns 200 with the not-found page.

## 8. Report and commit

Summarise in this order: what changed in the schema (with the migration file name), what the migration did to existing data, what code was updated, how it was verified, and anything left undone.

Commit only when asked. When committing, keep the database change separate from the feature that uses it, and make sure each commit passes typecheck and lint on its own:

```
feat(db): add launched_at to products      # schema, migration, seed, types, queries
feat(catalog): sort new arrivals by launch  # pages and components
```
